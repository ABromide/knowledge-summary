可靠性与可观测性 ​

AI 系统的可靠性不能简化为“Pod 会自动重启”。训练作业可能运行数天，任何一次节点、网络或存储故障都会损失昂贵进度；推理服务面对动态批处理、长上下文和显存压力，进程仍然存活时也可能已经无法在时限内返回结果。更棘手的是，系统包含数据、模型、框架、通信库、设备、调度器和服务网关，故障常沿多层放大：一个慢盘造成 dataloader 饥饿，继而让某个 rank 落后，最终所有 GPU 在集合通信处等待。

可靠性工程的核心，是为每类工作负载定义“正确服务”的含义，并建立从用户症状到基础设施证据、从故障检测到安全恢复的闭环。可观测性不是收集尽可能多的日志，而是让工程师能回答：用户受到了什么影响、哪一层首先偏离、恢复动作是否有效、同类问题能否提前阻断。

交互式决策卡可靠性控制面

从症状出发选择恢复层级，避免所有故障都直接重启整个任务。

一、先建立故障模型 ​

训练与推理共享硬件，却有不同的失败语义。训练强调进度与最终产物：worker 短暂退出未必意味着任务失败，只要能够从一致检查点恢复；推理强调逐请求结果：即使副本随后恢复，已超时或返回错误的请求仍然消耗错误预算。平台应为二者分别定义状态机，而不是统一成 Running、Failed、Succeeded 三个状态。

故障可以按影响范围分层：

层次典型现象需要保留的证据
请求超时、取消、输出不合法、限流request id、模型版本、token 数、排队与执行时长
进程OOM、死锁、非法访问、框架异常rank、退出码、栈、显存、最近一步
节点GPU Xid、磁盘满、网卡抖动、kubelet 失联节点事件、设备健康、内核日志、拓扑位置
集群调度拥塞、镜像仓库或对象存储异常队列、控制面延迟、依赖服务 SLI
数据与模型坏样本、权重损坏、版本错配、质量回退数据版本、校验和、模型 manifest、评测结果

还应区分 crash、hang、slow 和 wrong。Crash 最容易被发现；hang 可能表现为进程仍在但 step 不再前进；slow 让尾延迟恶化或训练吞吐缓慢下降；wrong 则返回格式正确但语义错误的结果，是最危险也最难只靠基础设施指标发现的故障。每一类都需要不同检测：退出码、进度心跳、性能基线和质量评测。

二、训练可靠性：恢复进度而不是重启进程 ​

分布式同步训练具有组语义：一个 worker 退出后，其余 worker 往往无法继续使用原有进程组。根据 PyTorch torchrun Elastic 文档，worker 故障会触发整个 worker group 停止并在 max_restarts 范围内重启；成员变化时 rank 和 world size 可能重新分配，因此训练代码不能假设 rank 在重启后稳定。Elastic 解决的是进程编排，不会自动保存模型进度。没有检查点的自动重启只是更快地从头再来。

一个可恢复检查点至少包含模型参数、优化器状态、学习率调度器、全局 step、随机数状态、数据采样位置和混合精度 scaler。若只保存权重，恢复后可能重复消费数据、改变随机序列或丢失优化器动量，结果与连续训练出现难以解释的偏差。保存动作必须形成逻辑一致的快照：不能让不同 rank 写入不同 step 的状态，再由一个“成功标记”把它们误认为同一版本。

PyTorch Distributed Checkpoint支持多 rank 并行保存与加载，并可在加载时重新分片，使检查点能够跨不同并行拓扑恢复。工程上还要补齐存储事务：先写临时目录，完成所有 shard、元数据和校验和后再原子发布 manifest；恢复器只读取已提交版本。异步保存可降低训练暂停时间，但必须控制后台写入占用的 CPU、内存和带宽，并确保任务被终止前完成或回退到上一个完整版本。

训练 hang 需要进度看门狗。每个 worker 可上报 step、最近一次 batch 完成时间和关键 collective 阶段；控制器观察全局最小 step 是否持续推进。若某 rank 心跳正常但长期落后，应先抓取进程栈、NCCL 状态、GPU 利用率和数据读取延迟，再执行恢复。直接 kill 虽然能释放资源，却会抹去最有价值的现场。诊断采集需要上限，不能为了保留证据无限阻塞昂贵节点。

三、推理可靠性：保护尾延迟与正确性 ​

在线推理的故障往往先表现为排队增长。Prefill、decode 和 KV cache 共享 GPU，长请求会挤压短请求；动态批处理提升吞吐，却可能增加等待；流量继续上升后，显存抖动、超时重试和并发放大形成正反馈。服务若只看平均 GPU 利用率，会在用户 P99 已经失控时仍显示“一切繁忙但正常”。

推理请求应拆分为入口排队、调度等待、prefill、逐 token decode、后处理和网络发送。核心指标包括首 token 延迟 TTFT、相邻 token 延迟 ITL、端到端延迟、输出 token 吞吐、在途请求、KV cache 使用率、批大小、取消率和按原因分类的失败率。NVIDIA Triton Metrics区分 request、inference 与 execution 计数：启用 batching 后三者不再相等，正可用来推导平均批量并判断吞吐提升来自合批还是流量变化。

过载时必须主动降级。无限接收请求只会把确定的拒绝变成更晚的超时，并占用更多显存与连接。入口层应设置并发、队列长度、输入 token 和最大输出 token 预算；超过安全水位时返回明确的可重试或不可重试错误。服务内部可以按租户与优先级分队列，避免离线批量请求压垮交互流量。Triton Rate Limiter能够按模型实例、优先级和资源约束控制执行速率，主要价值不是让服务器更快，而是避免模型同时执行造成超额资源压力。

健康检查要反映不同语义。Kubernetes 探针文档区分 startup、liveness 和 readiness：startup 为慢启动模型留出加载窗口；readiness 决定是否接收流量；liveness 用于确认进程是否已无法自愈。模型仍在加载、显存水位过高或依赖未就绪时应让 readiness 失败，但不要用过于敏感的 liveness 制造重启循环。仅检查 HTTP 端口不够，readiness 至少应确认目标模型版本已加载、执行队列未失控，并可用轻量请求验证关键路径。

四、从用户体验定义 SLO ​

SLO 应从用户可观察结果倒推，而不是从现成 Prometheus 指标挑一个好看的数字。Google SRE 的 SLO 章节将 SLI 定义为服务行为的量化指标，SLO 是其目标范围；平均值常会掩盖长尾，因此延迟目标通常使用分位数。对 AI Infra，训练平台用户与推理 API 用户关心的指标不同。

训练平台可以设置：99% 已准入作业在约定时间内启动；99.5% 的 checkpoint 在目标窗口内形成可恢复版本；可恢复故障后 95% 作业在十五分钟内继续推进；月度因平台故障丢失的计算量不超过已用 GPU-hours 的某个比例。这里不能承诺“作业永不失败”，因为用户代码、数据错误和主动取消不属于平台可控失败，SLI 必须明确事件分类。

推理服务可设置：成功率、TTFT、端到端延迟和正确性。流式生成服务应按输入/输出 token 桶或服务等级拆分目标，例如短交互请求 99% TTFT 小于阈值，长上下文请求使用另一套目标。若把所有请求混在一起，流量结构变化就会让指标失去可比性。错误率分母也要写清：客户端取消、非法参数、平台限流、模型执行失败是否计入，各自应有独立维度。

错误预算等于允许未达到 SLO 的空间。它不是容忍故障的借口，而是发布与风险决策的共同尺度。预算健康时可继续变更；消耗速度过快时降低发布频率、限制高风险迁移并优先处理可靠性。对于 30 天 99.9% 成功率目标，预算是 0.1% 合格请求；真正有操作价值的是 burn rate：当前消耗速度若持续，预算会在多久后耗尽。快燃烧告警用于发现急性事故，慢燃烧告警用于发现持续小幅回退。

五、指标、日志、追踪和事件如何协作 ​

指标适合回答“影响多大、何时开始”，日志解释局部状态，追踪连接一次请求的跨层路径，事件记录控制面决策。四者必须共享少量稳定关联键：cluster、namespace、tenant、workload、run id、pod、node、model、model version、request id。GPU UUID、rank、数据版本等高基数属性可留在日志或按需追踪中，不能无节制塞入时序指标标签。

训练观测面应把 step time 分解为数据、前向、反向、优化器、checkpoint 与通信阶段，并同时显示 GPU 利用率、显存、功耗、网络吞吐、磁盘与 CPU。单一 GPU utilization=100% 不能证明有效训练，忙等或异常 kernel 也可能让设备繁忙。更接近用户价值的黄金信号是样本或 token 吞吐、step 是否推进、损失是否有限、检查点是否新鲜。

推理追踪要跨越网关、路由器、批处理器、模型实例和流式返回，但不能默认记录 prompt、输出、访问令牌或个人数据。内容采样需显式授权、脱敏、限制保留期；普通追踪只保存长度、哈希、状态码和阶段耗时。诊断价值与数据风险必须同时评估。

告警应指向行动。页面告警表示必须立即人工介入，工单表示可在工作时间处理，日志用于事后分析。症状告警优先于原因告警：先根据成功率和尾延迟告知用户影响，再用 GPU Xid、队列积压或存储错误辅助定位。每条告警应附带 SLO 影响、受影响租户、最近变更、拓扑聚类、仪表盘与运行手册；不能只发送“某 Pod 重启一次”。

六、恢复自动化必须有边界 ​

自动恢复适合结果确定、动作幂等、风险受限的场景：重启单个无状态副本、从最近完整检查点重建 worker group、隔离明确报告硬件错误的节点、将新版本流量回滚到已验证版本。涉及数据覆盖、大规模驱逐、跨租户资源抢占或无法确认根因时，应转为人工审批。

恢复流程可以固定为五步：检测并确认影响；冻结或限制进一步放大；保存现场证据；执行最小恢复动作；验证用户 SLI 与业务正确性。Pod 变绿不是完成，训练必须重新推进并产生新 checkpoint，推理必须通过真实请求验证延迟与输出。若恢复后指标再次恶化，自动化应停止重试并升级，而不是无限重启。

节点故障后不要立即重新投入资源池。对 GPU Xid、ECC、RDMA 或文件系统错误，应按规则 cordon，运行硬件和通信诊断，合格后再解除隔离。否则一个“偶发坏节点”会连续污染不同租户任务。设备维修记录要和调度标签联动，使可靠性数据反向影响放置。

计划维护需要中断预算。Kubernetes 的 PodDisruptionBudget 约束 eviction API 发起的自愿中断，却不保证抵御节点掉电等非自愿故障，也不限制 Deployment 自身滚动更新；因此它是维护协商机制，不是完整高可用方案。训练作业在维护前应保存检查点并停止新准入，推理服务按可用区逐批迁移并持续检查 SLO，避免一次 drain 触发大规模冷启动。

七、用演练验证，而不是相信设计 ​

可靠性能力必须通过故障注入和恢复演练证明。训练场景可依次测试单 worker 退出、整机掉线、网络延迟、对象存储短暂不可用、坏 checkpoint 和数据 shard 错误；推理场景测试模型加载失败、GPU OOM、慢请求洪峰、单区失效、下游超时和错误模型发布。每次只扩大一个故障维度，预先定义停止条件，避免演练本身成为事故。

验收不只看“服务最终恢复”，还要记录检测时间 MTTD、缓解时间、完全恢复时间、丢失计算、失败请求和人工步骤。演练发现的手册缺口、权限问题、遥测缺失应进入明确负责人和期限的改进项。若恢复必须依赖某位工程师记住隐藏命令，那仍然是未工程化的单点。

八、故障演练矩阵与 SLO 验收 ​

演练前先固定安全边界：限定租户、资源池、流量比例和最长持续时间，确认停止开关与值班负责人，保存基线指标并验证备用容量。故障注入对象必须能够精确定位，禁止用模糊标签批量终止节点。演练期间若错误预算燃烧率、失败请求或丢失计算超过预设上限，应立即停止注入并执行恢复；停止条件本身也要在演练报告中验证，而不能只写在方案里。

一组最小演练矩阵应覆盖以下闭环：

注入场景期望检测恢复动作通过标准
单个训练 worker 退出进程组失败与首个根因关联到同一 run重建 worker group 并加载完整检查点step 继续增长，数据位置与学习率正确
训练节点无响应节点心跳与训练进度同时告警隔离节点，在新节点恢复不再次调度到坏节点，丢失进度低于上限
检查点写入中断临时版本未出现提交标记回退上一完整版本校验和通过，不读取半成品 shard
推理副本显存耗尽执行失败、队列和尾延迟共同升高摘除副本、限制并发、扩展健康副本成功率恢复且没有重试风暴
错误模型小流量发布质量集或契约指标偏离停止放量并回滚制品摘要新流量归零，旧版本 SLI 恢复
单个可用区失联黑盒成功率按区域下降路由到剩余区域并限制低优先级流量全局错误预算消耗受控

SLO 验收首先核对口径。每个指标必须声明分子、分母、统计窗口、排除事件、数据来源和迟到数据处理规则。训练启动 SLI 要明确从“提交”还是“准入”开始计时；恢复 SLI 要明确以进程启动、加载完成还是新 step 产出为终点；推理成功率要分别统计用户取消、限流、服务错误和模型错误。使用同一批事件离线重算时，仪表盘、告警和月报应得到一致结果。

随后验证告警对预算的响应。向测试流量注入短时高错误率与持续低错误率，确认快燃烧窗口能及时通知急性事故，慢燃烧窗口能捕获长期回退，同时正常流量波动不会频繁翻页。告警触发后，值班人员应从通知直接进入受影响租户、模型版本、最近变更和恢复手册；若还需要人工拼接多个系统的标识，关联链路仍未验收通过。

每次演练的证据包至少包含时间线、注入配置、指标快照、关键日志与追踪、控制面事件、自动动作、人工决策和用户影响。恢复后再执行一次真实训练步或真实推理请求，证明业务路径可用；仅凭 Pod Ready 或告警恢复为绿色不能结案。报告中的改进项要有负责人、截止时间与复验场景，下一轮演练必须检查旧问题是否真正关闭。

演练频率按变化与风险决定：推理发布和检查点恢复可以在持续交付中自动验证，节点与可用区故障适合定期受控演练，跨集群容灾则在重大架构或依赖变更后重新验证。若某项 SLO 连续耗尽预算，应暂停扩大故障注入范围，先修复已知薄弱环节。演练的目标是积累恢复证据，不是追求注入场景数量。

可靠性不是“永不失败”，而是故障可被及时看见、影响被限制、状态可被重建、恢复结果可验证。对高成本 AI Infra 而言，最重要的产物不仅是模型和响应，也包括每一次计算进度的可恢复性与每一次平台决策的可解释性。
