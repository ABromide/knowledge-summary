Scaling Law 与工作负载建模 ​

Scaling Law 的工程价值，不是证明“大就一定好”，而是在昂贵训练开始前建立一套可校准的资源假设：有限算力应该分给多少参数和多少 token，目标 loss 是否能由小实验外推，数据能否持续供给，集群要运行多久，任何一项偏离计划又会损失多少时间。工作负载建模则把这些假设继续翻译成设备小时、显存、通信、存储与可靠性要求。前者回答“训练什么”，后者回答“怎样把它稳定训练完”。

本章学习目标阅读前先建立清晰预期
理解缩放规律的适用边界建立训练容量预算用实测数据校准计划

1. 把缩放规律当作经验模型，而不是自然定律 ​

Kaplan 等人对语言模型的交叉熵进行系统实验，观察到 loss 随模型参数量、数据量和训练计算量呈近似幂律变化，而且趋势跨越多个数量级。论文同时强调，在其研究区间内，宽度、深度等结构细节相对不是主要变量。这一结论让小规模实验可以服务于大训练决策，但它描述的是特定数据分布、模型族和优化设置下的经验关系，不保证在架构、分词器或数据质量显著改变后仍保持原指数。《Scaling Laws for Neural Language Models》

一个实用的抽象是把可约 loss 写成计算量的幂函数，再加上不可约项：L(C) = a · C^b + c。其中 C 是训练计算量，a 与训练配方有关，负指数 b 描述追加计算带来的边际收益，c 则代表在当前任务、数据与模型族下难以继续压低的部分。幂律意味着收益递减：计算量翻倍通常只带来稳定但越来越小的 loss 改善。因此容量评审不应只问“多加一倍卡能否训练”，还要问“预期改善是否足以覆盖新增成本和机会成本”。

GPT‑4 技术报告展示了这种方法的工程化用法：团队用至多低四个数量级的计算实验拟合带不可约项的曲线，并在大训练早期就预测最终 loss；对一部分 HumanEval 问题，也用更小规模实验预测通过率。但报告同时指出，单个任务的表现可能随规模变差，某些能力依然难以预测。因此 loss 外推适合做训练健康度与基础容量基线，不应被包装成对所有下游能力、安全性或产品价值的承诺。OpenAI：GPT‑4 Technical Report

2. 参数与数据必须共同进入预算 ​

早期缩放研究倾向于在固定计算下选择更大的模型并较早停止训练。Chinchilla 研究扩大了实验矩阵：团队训练了四百多个、参数规模从七千万到一百六十多亿、数据量从五十亿到五千亿 token 的模型，得到不同的计算最优分配。其核心结论是，在研究范围内，模型参数和训练 token 应更均衡地扩展；参数量翻倍时，token 量也应近似翻倍。70B Chinchilla 与 280B Gopher 使用相同计算预算，却因模型更小、数据更多而取得更好结果。《Training Compute-Optimal Large Language Models》

这不是一句可以永久套用的“每参数固定若干 token”口号。计算最优点会受数据质量、重复率、学习率日程、模型结构以及训练后推理成本影响。若模型会被高频服务，稍小但训练更充分的模型还可能降低长期推理费用；若数据极为稀缺，继续增加 token 可能只是在重复样本；若目标是一次性的能力探索，训练成本又可能比部署成本更重要。正确做法是保留 N（参数量）、D（训练 token）、C（计算量）三个独立变量，用本项目的小模型实验重新拟合，而不是从公开模型反推一个万能比例。

数据预算也不能只写“共有多少 TB”。token 化后的有效数据量才与训练步数直接相关，还应分开记录原始 token、清洗后 token、去重后 token、混合采样后的实际曝光量，以及每个数据域被重复的次数。数据准备晚于算力到位，会让昂贵集群等待；数据版本在缩放实验与正式训练之间变化，则会让拟合曲线失去可比性。

3. 用同一组单位描述训练工作负载 ​

容量模型首先统一符号：

符号含义需要实测或确认的内容
N有效参与计算的参数量密集参数、MoE 激活参数分别记录
D本次训练处理的 token 数去重、采样和重复曝光后的实际值
S序列长度不只记上限，还要记长度分布与 padding
B全局 batch 的 token 数micro batch、梯度累积和数据并行乘积
F_step每步实际浮点操作量用 profiler 或框架计数器校准
P_peak单设备理论峰值明确精度、稀疏条件与功耗档位
u端到端有效利用率包含算子、通信、气泡和数据等待
G设备数量同时记录可用率和预留备件

密集自回归 Transformer 常用 C ≈ 6ND 作为预训练计算量的一阶估算：一次前向约为 2N 浮点操作，反向传播约为前向的两倍，合计得到每 token 约 6N。它适合在立项阶段比较方案，却不是结算公式。词表投影、注意力的序列长度项、激活重计算、门控、稀疏专家、padding 和特定实现都会改变实际工作量。PaLM 论文在描述 540B 模型和 6144 个 TPU v4 芯片的训练时，也把硬件、并行系统与训练规模放在同一个实测框架中，说明大模型数字必须与系统配置一起解读。《PaLM: Scaling Language Modeling with Pathways》

理想训练时间可粗估为 T_ideal = C / (G · P_peak)，计划时间则是 T_plan = C / (G · P_peak · u)。这里最危险的是把 u 默认为一个乐观常数。有效利用率至少包含：单算子未达到峰值、输入形状不友好、流水线气泡、集合通信、负载不均、数据加载、checkpoint、评估、故障重启与运维暂停。预算表应把可优化损失和不可避免损失拆开，并用短跑实测更新，而不是在汇报中把它们都藏进“GPU 利用率”。

4. 从模型形状推导显存与通信 ​

“总显存大于权重大小”远不足以证明训练可运行。混合精度 Adam 训练通常同时存在低精度参数、梯度、FP32 主参数、两个优化器矩，以及随 batch、层数和序列长度变化的激活。还要预留临时 buffer、通信 bucket、CUDA graph 或编译缓存和显存碎片。激活检查点用额外计算换显存，ZeRO 则逐阶段切分优化器状态、梯度和参数；DeepSpeed 官方说明中，ZeRO‑3 会在数据并行进程间切分完整模型状态，并在前后向需要时收集对应分片。DeepSpeed：ZeRO 官方教程

因此显存模型至少分成四栏：按参数量线性增长的模型状态、按 micro batch × sequence × hidden × layers 增长的激活、与算子实现有关的临时空间，以及安全余量。先用解析估算排除明显不可行方案，再用目标形状跑一至数步记录峰值；只测短序列或只完成前向都会严重低估正式训练。

通信模型从并行策略推导。数据并行主要同步梯度，张量并行在层内反复执行 AllReduce 或 AllGather，流水线并行传递阶段边界激活，专家并行产生与路由相关的 AllToAll。Megatron‑LM 的大规模训练研究把张量、流水线和数据并行组合到数千 GPU，并指出朴素组合会受到跨节点通信和设备等待限制；其一万亿参数实验报告的每 GPU 吞吐约为理论峰值的 52%，恰好说明“设备数乘峰值”不是交付速度。《Efficient Large-Scale Language Model Training on GPU Clusters Using Megatron-LM》

估算通信时，不能只用消息字节除以链路标称带宽。还要加入集合算法、拓扑跳数、并发流、协议效率和小消息延迟，并检查通信能否被计算覆盖。最有效的早期决策通常不是寻找最复杂的并行组合，而是把高频张量并行限制在高速域内，把跨节点带宽留给频率较低、消息较大的通信。

5. 把一次训练拆成可观测的时间账本 ​

工作负载模型应按训练步建立时间账本：前向、反向、优化器、通信暴露时间、输入等待和其他框架开销的总和等于稳态步时；在此之外，再单独加入编译预热、评估、checkpoint、故障恢复和计划停机。这样当最终周期超出预算时，可以定位偏差来自模型计算估错、利用率下滑，还是非稳态事件过多。

建议至少跑三层校准实验：

  1. 单设备算子与显存校准。 使用目标精度和目标形状，确认 kernel、峰值显存和数值稳定性。
  2. 单节点并行校准。 扩大到完整高速互连域，测量 batch 扩展、通信覆盖和数据输入。
  3. 多节点弱扩展校准。 保持每设备工作量近似不变，逐级扩大规模，拟合吞吐、尾部步时和故障率。

每一层都保留模型提交、数据版本、容器镜像、编译选项、设备功耗、拓扑和 profiler 原始结果。只保存“tokens/s 最好值”无法复现实验，也无法解释正式训练为何回退。

6. 基准测试必须固定质量目标 ​

硬件基准常见误区是只比较峰值 FLOPS 或若干分钟的吞吐。MLPerf Training 的定义更严格：每个工作负载绑定数据集、模型和质量目标，核心指标是达到目标质量所需的墙钟时间；Closed division 约束实现以便同类比较，并通过多次运行和去除极值降低方差。MLCommons：MLPerf Training

内部容量测试也应借鉴这个原则。固定 token 数的吞吐测试适合比较系统效率，固定 loss 或评估门槛的达标时间才适合比较完整训练方案；两者不能混用。如果新优化提高每秒 token，却改变收敛、数值精度或有效 batch，最终达标时间可能更差。对外部榜单还要核对软件版本、可用性类别、设备数量、功耗和是否使用稀疏峰值，避免把不可采购的预览系统或不同质量目标放在同一张成本表里。

7. 决策案例：训练周期为何比预算慢四分之一 ​

假设容量表预测一项预训练需要四十天，正式运行一周后却按当前速度外推为五十天。此时不应立即增加设备，因为偏差可能来自总工作量、稳态效率或非稳态损失三类原因，盲目扩容甚至会放大通信开销。

第一步核对分母之前的工作量。检查实际 token 化后数据量、序列长度分布、padding 比例和训练总步数是否与立项表一致。若数据团队加入了新语料，或动态打包没有达到预期，实际 FLOPs 已经变化，原计划就需要重新基线化。还要确认梯度累积、激活重计算和评估频率是否在配置变更中被调整；这些变化不一定出现在模型参数量里，却会真实增加计算。

第二步只比较稳定窗口。取相同模型提交和数据区间，把前向、反向、优化器、暴露通信及输入等待分别与短跑基线对齐。若计算段变慢，检查算子形状、编译缓存、功耗限制和降频；若通信段变慢，检查跨节点映射、掉速链路与慢节点；若输入等待上升，查看数据分片热点、远端存储和解压线程。平均 GPU 使用率无法替代这份分解，因为通信等待时设备指标也可能显示繁忙。

第三步统计非稳态账目。把 checkpoint、在线评估、故障重启、坏节点隔离和人工暂停按事件累计，而不是摊平后消失在平均步时里。例如稳态吞吐只低百分之五，但每天因保存和故障损失近五小时，主要矛盾就是恢复与存储，而不是算子。反过来，如果非稳态损失很少而每步持续慢百分之二十，应优先修复执行效率。

处理方案必须给出可验证收益：缩短 checkpoint 周期也许降低单次中断损失，却增加写入频率；扩大数据并行也许提高总吞吐，却可能降低单卡效率；减少评估可以追回时间，却会拉长异常发现窗口。每个方案都应更新完成日期、失败风险和质量可见性，再决定是否接受。

进入正式训练前的验收清单 ​

  • 缩放拟合至少覆盖三个计算规模，正式训练点没有远离全部观测区间，残差和置信范围已保存。
  • 数据清单固定到不可变版本，token 数、重复曝光、域混合和保留验证集可追溯。
  • 目标模型形状完成前向、反向、优化器与保存恢复的连续验证，不以单步成功代替训练可运行。
  • 单卡、单节点和目标节点规模均有稳态 trace，容量表中的利用率来自这些测量而非历史经验值。
  • 故障演练验证从最近 checkpoint 恢复后，模型状态、优化器、学习率、随机数和数据游标保持一致。
  • 质量看板同时显示训练 loss、验证指标、吞吐、显存、通信暴露时间和异常事件，且为偏离预测区间设置处置责任人。
  • 乐观、基准、悲观三种日历计划均包含评估、保存和维护窗口，资源负责人已确认预留时间与替换节点。

只有以上证据齐全，容量评审才能回答“按什么条件能够完成”。否则一个精确到小时的日期，只是把尚未确认的假设伪装成承诺。

8. 一份可执行的容量评审顺序 ​

  1. 明确目标能力、验证集和允许的失败概率，避免先定卡数再寻找任务。
  2. 用多个小规模点拟合 loss 与参数、数据、计算的关系，并保留置信区间。
  3. 选择候选 N-D-C 组合，同时考虑训练成本、数据上限和长期推理成本。
  4. 推导 FLOPs、显存、通信和存储模型，用目标形状短跑校准所有系数。
  5. 从短跑数据计算有效利用率和扩展效率，再确定设备数与日历周期。
  6. 把 checkpoint、评估、故障和维护加入时间账本，做乐观、基准、悲观三种情景。
  7. 设立继续、调整或停止训练的检查点；正式运行中持续比较实际曲线与预测区间。

最终交付物不是一个看似精确的设备小时，而是一组可追溯假设及其敏感性。Scaling Law 给出方向，工作负载模型暴露约束，在线观测不断修正两者。只有预测、实测和质量目标形成闭环，扩展才是工程决策，而不是规模叙事。
