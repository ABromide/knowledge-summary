调度平台与多租户治理 ​

AI 集群调度的本质，是把异构且关联的算力，以可预测的方式交付给不同团队。训练与推理还要同时处理 GPU 型号、显存容量、NVLink/NVSwitch、NUMA、RDMA、机架与可用区、数据位置、队列优先级、作业整体启动等约束。只要其中一个约束缺席，最终就会以低利用率、长排队、通信降速或租户争抢的形式出现。

因此，成熟的 AI 调度平台不是一个更复杂的 kube-scheduler 配置，而是由四层控制面组成：资源层准确描述设备，放置层寻找可行拓扑，准入层决定谁在何时使用多少资源，治理层建立身份、配额与隔离。它们分别回答“有什么”“放在哪”“何时轮到”“能否互相影响”。

交互式决策卡调度策略选择

选择作业形态，查看准入与放置阶段应该优先解决什么。

推荐关注点设备健康与 NUMA 局部性优先

一、从单 Pod 放置到工作负载交付 ​

Kubernetes 的调度循环先从队列中取出待调度 Pod，再过滤不满足硬约束的节点，对可行节点评分并选出目标，最后进入绑定循环。调度框架把这些步骤拆成 QueueSort、PreFilter、Filter、PostFilter、PreScore、Score、Reserve、Permit、PreBind、Bind、PostBind 等扩展点；插件能够在不改写调度器主干的前提下插入策略。Kubernetes 调度框架文档强调，调度循环是串行的，而绑定循环可以并发执行。这一差异意味着昂贵的过滤或评分插件会直接降低全局调度吞吐，平台团队必须把插件耗时、候选节点数量和队列等待时间当作控制面性能指标。

调度动作至少包含三个不同判断：

判断典型问题失败后的表现
可行性节点是否有足够资源，标签、污点、亲和性是否满足Pod 保持 Pending
优选性在多个可行节点中，哪个放置能降低碎片或改善拓扑能运行但成本或性能不理想
准入性租户是否有额度，队列是否轮到，该作业是否值得现在启动作业在队列中等待

原生调度器主要解决前两项。若把准入问题也塞进 Pod 的优先级和抢占，就会出现两个副作用：第一，已创建的海量 Pod 持续冲击调度队列；第二，平台难以对“一个训练作业”执行整体公平、借用和撤销。更清晰的做法是先在队列控制器中准入工作负载、锁定配额与资源类别，再允许它创建或放行 Pods。于是，调度对象从 Pod 上升为 Job、PodGroup 或 Workload，治理单位从一张卡变成一次可计费、可观察、可恢复的任务。

二、队列不是等待列表，而是资源承诺系统 ​

AI 平台常见三级结构：团队使用本地队列提交任务；本地队列映射到集群级资源池；多个资源池组成可共享余额的组织或 cohort。队列配置应声明可用的 GPU flavor、名义配额、可借用上限、借出保护、优先级和公平策略。这样，平台能区分“没有资源”“本团队额度不足”“正在借用其他团队额度”“被更高优先级任务抢占”，而不是把所有状态都压成一个模糊的 Pending。

公平也不是简单的先进先出。短实验若永远排在大型训练之后，交互效率会很差；大作业若总被小任务插队，又可能永久饥饿。常见策略可以组合使用：

  • 在同一优先级内按等待时间排序，并用 aging 逐步提高长期等待任务的权重；
  • 给生产推理、故障恢复、正式训练和探索实验设置少量、稳定的优先级层级，避免每个团队自定义等级；
  • 对组织资源按 dominant share 计算公平度，避免只看 GPU 数而忽略 CPU、内存或高端网络；
  • 允许空闲配额借用，但明确可抢占条件、宽限期和最大借用量；
  • 把预计运行时间、检查点能力和重启成本纳入抢占策略，避免为了释放一张卡而销毁数小时不可恢复进度。

对紧耦合分布式训练，单个 Pod 被放置并不等于作业能够前进。若两个八卡任务各拿到四张卡，它们可能同时等待剩余资源，形成“资源已占用、计算未开始”的死锁。Gang scheduling 用 minCount 表示最小同时启动规模：只有整个组达到门槛，Pods 才一起绑定；否则全部回到不可调度队列。Kubernetes Gang Scheduling将它描述为 all-or-nothing，并依赖 PodGroup 的整体调度周期。当前这组能力仍需关注具体 Kubernetes 版本和 feature gate，生产平台不能把 alpha API 当作无条件稳定接口。

三、DRA：把设备从整数扩展资源变成可声明对象 ​

传统设备插件通常把 GPU 暴露为 nvidia.com/gpu: 1 这样的整数扩展资源。它适合“同质、不可分、无需额外参数”的设备，但无法自然表达 GPU 型号、显存、MIG profile、固件能力、共享方式，或“必须成组分配的设备”。标签和 node affinity 能补充一部分约束，却把设备细节抬升成节点属性，容易造成标签爆炸，也无法对单台节点上的不同设备做精确选择。

Kubernetes Dynamic Resource Allocation把设备选择提升为结构化资源声明。设备驱动通过 ResourceSlice 发布可分配设备及属性；管理员用 DeviceClass 提供稳定的逻辑类别；工作负载通过 ResourceClaim 或模板声明需求；调度器将 Claim 与 Pod 放置共同求解，节点侧驱动完成准备与清理。对用户而言，请求可以从“任意一张 GPU”演进为“满足某组属性的设备”；对平台而言，驱动信息、策略默认值和用户请求各自处于清晰边界。

DRA 的价值不只是字段更多，而是把资源生命周期接入调度事务。平台必须观察 Claim 的创建、分配、准备、消费和释放，不能只以 Pod 是否 Running 判断资源状态。DeviceClass 应保持少而稳，以“训练卡”“低延迟推理卡”“可切分开发卡”等意图隐藏底层硬件换代。

四、拓扑感知：可运行不等于高效运行 ​

分布式训练的每一步通常在集合通信处同步，最慢 rank 决定全局步时。八张卡即使数量足够，如果跨越低带宽链路，性能也可能显著差于同一 NVLink 域；跨机训练若落到不同机架或可用区，延迟、拥塞与故障相关性都会变化。因此，放置目标不是简单的“越近越好”，而是让通信密集任务尽量紧凑，让高可用副本合理分散。

拓扑策略可分为四个尺度：

尺度训练倾向在线推理倾向风险
GPU / NUMA同 socket、同高速互联域模型实例靠近 CPU 与网卡局部资源碎片
节点多卡优先占满单机多副本避免全在单机大节点成为故障集中点
机架通信作业尽量同机架副本跨机架分布ToR 带宽与机架故障
可用区单次训练减少跨区流量服务跨区容灾跨区成本和数据一致性

Pod Topology Spread Constraints通过 topologyKey、maxSkew、minDomains 和 whenUnsatisfiable 描述副本在拓扑域间的均衡程度。DoNotSchedule 是硬约束，可能在标签缺失或容量不足时阻塞发布；ScheduleAnyway 是软偏好，能保持可用但不保证达到目标。对推理副本，可用区级 spread 常用于降低相关故障；对通信密集训练，反而可能需要 PodGroup 级的同域约束。不能把一套“分散最佳实践”机械应用到所有 AI 负载。

拓扑感知还要与碎片治理结合。持续把小任务塞到每台八卡节点的一张卡上，会让集群拥有很多“空闲 GPU”，却无法容纳任何八卡作业。评分策略可优先填满已被部分使用的节点，为大作业保留完整节点；也可按资源池设置不同整理目标：开发池追求共享率，训练池追求连续大块容量，推理池追求副本故障分散。单一全局评分函数很难同时满足三者。

五、GPU 共享：利用率、性能与隔离的三角关系 ​

GPU 共享主要有进程并发、time-slicing、MPS 和 MIG 等路径。平台不能只宣传“切成几份”，而应明确每种方式隔离了什么、没有隔离什么。NVIDIA GPU Operator 的 time-slicing 文档指出，时间切片让多个副本复用同一物理 GPU，但副本之间没有显存或故障隔离；申请多个 time-sliced 资源也不等于获得成比例的算力。它适合低占用实验、Notebook 和容忍抖动的开发推理，不适合把份额当成确定性容量承诺。

MIG 将支持的 GPU 切为预定义实例，提供硬件层面的显存与故障隔离，资源轮廓更容易计费和设定 SLO，但 profile 固定、重配置存在运维成本，碎片也可能从“空闲卡”转变为“空闲但尺寸不匹配的实例”。MPS 更偏同一 GPU 上 CUDA 进程的并发执行，能够提高某些小 kernel 工作负载的利用率，但隔离与运维语义不同于 MIG。平台应把共享模式做成资源类别，并用准入策略阻止生产服务误用弱隔离池。

六、多租户：命名空间不是安全边界的全部 ​

多租户首先要定义威胁模型。内部研发团队之间通常是有限信任，主要风险是误操作、资源争抢与数据越权；面向外部客户或运行不可信代码时，则要考虑容器逃逸、设备 DMA、主机内核和共享存储等更强风险。隔离强度应沿身份、控制面、网络、存储、节点和设备逐层设计，而不是仅创建 namespace。

交互式决策卡多租户隔离决策

资源隔离需要同时覆盖容量、性能、数据和控制面。

推荐关注点先限制可占用资源总量

团队共享集群，需要避免单租户耗尽 GPU。

主要收益
  • 边界清晰
  • 便于成本归属
代价与限制
  • 闲置配额降低利用率
  • 借用规则更复杂
验证动作
  • 验证 hard quota
  • 记录借用与回收
  • 检查队列公平性

Kubernetes 多租户指南建议将 namespace 与 RBAC、ResourceQuota、NetworkPolicy 等机制组合。落到 AI 平台，最小治理基线包括：

  1. 用户通过企业身份进入租户或项目，工作负载使用独立 ServiceAccount，默认不挂载不必要的 API 凭据；
  2. RBAC 仅允许租户访问自己的命名空间与任务对象，集群级设备类、RuntimeClass、Webhook 和存储类由平台管理；
  3. ResourceQuota 限制对象数量和通用资源，队列系统限制跨命名空间的 GPU 配额与借用；
  4. NetworkPolicy 从默认拒绝开始，只开放 DNS、制品库、数据源与明确的分布式训练端口；
  5. 数据集、模型、检查点使用租户身份授权，临时凭据短期下发，不写入镜像和任务清单；
  6. 高风险或不可信任务进入独立节点池、沙箱运行时、虚拟机甚至独立集群，不能把容器本身当作强安全边界。

七、抢占、借用与容量规划 ​

抢占是恢复资源承诺的手段，不是日常排队算法。优先级设计过细会诱导团队不断抬高等级，最终所有任务都“最高优先”；频繁抢占会浪费训练进度、污染缓存并制造恢复风暴。平台应只允许少数受治理的 PriorityClass，并把抢占决策解释为具体事件：谁因何种策略释放了哪些资源、损失了多少计算、何时能够重新入队。

可抢占训练必须先证明可恢复。平台可要求作业声明最近检查点时间、预计恢复耗时与最小运行窗口；检查点过旧时，先触发保存或延迟抢占。在线推理则通常通过副本预算和渐进迁移释放节点，不能直接以训练式 kill-and-requeue 处理。对于借用资源，低优先级租户应预期被收回，但平台仍应给出通知、宽限期和最大并发驱逐量，防止同时终止大量任务压垮对象存储。

八、平台落地顺序与验收指标 ​

验收指标也要覆盖用户体验与系统效率：

  • 排队时间按资源类、租户、优先级和作业规模统计 P50/P95/P99；
  • 准入后启动成功率，以及镜像、存储、设备准备导致的超时比例；
  • gang 作业半启动时间应接近零，无法成组放置时不长期占用 GPU；
  • 同类训练在不同拓扑上的 step time 与通信占比可比较；
  • GPU 碎片率能够区分“数量不足”和“形状不匹配”；
  • 借用量、抢占次数、丢失计算时长和检查点恢复成功率可追踪；
  • 每个调度结论都能从事件中回答：为何等待、为何选此节点、为何被抢占。

九、调度决策记录与准入验收 ​

调度策略只有可回放，才可能被治理。每次准入应保存不可变的决策快照，包括作业资源请求、队列与租户、优先级、配额余额、借用关系、候选设备类、拓扑要求、集群可用容量和策略版本。进入放置阶段后，还应记录各过滤条件排除了多少节点、最终候选节点的评分分解、设备声明分配结果以及绑定时间。这样，平台升级策略后可以用历史快照离线重放，判断新规则是否会改变等待顺序、放置位置或抢占对象，而不必直接在生产流量上试错。

用户侧不应只看到 Pending。建议把等待原因归一为资源总量不足、租户配额不足、等待借用额度、缺少完整 gang、拓扑无可行域、设备准备失败和安全策略拒绝等有限状态。状态变化时同时写入时间、触发条件和建议动作。例如“拓扑无可行域”需要展示哪些域缺少几张目标设备，而不是让用户反复修改亲和性猜测；“配额不足”则应区分本队列额度用尽与上级资源池整体用尽。

准入前检查应至少回答以下问题：

  1. 资源请求是否完整，DeviceClass、共享模式和运行时是否存在，CPU、内存、临时存储能否与 GPU 同时满足；
  2. 分布式任务的 worker 数、minCount、端口和网络要求是否一致，部分启动是否真的能够推进；
  3. 所需拓扑标签覆盖率是否达标，每个候选域是否存在足够的连续容量，硬约束失败时是否允许降级；
  4. 租户名义配额、借用上限和抢占策略是否明确，被抢占任务是否有足够新的检查点；
  5. ServiceAccount、网络策略、存储授权和镜像来源是否满足租户基线，敏感任务是否进入了正确隔离池。

验收时要用冲突场景而非单任务冒烟测试。可以同时提交短实验、大规模 gang、生产推理扩容和可抢占训练，验证高优先级并不会无限压制普通队列，借用资源能够在约定窗口内被收回，大作业不会因碎片永久饥饿。再人为移除部分机架标签、使一种 DeviceClass 暂时不可用、制造设备准备超时，确认系统会释放预留、更新原因并重试其他可行资源，而不是反复命中同一故障节点。

策略发布采用影子评估更安全：新策略只计算不绑定，把结果与当前策略并排比较。差异应按租户公平度、排队分位数、跨域放置、碎片和预计抢占损失分类；超出阈值时阻止切换。正式启用后保留旧策略配置和队列快照，若出现调度吞吐下降或大面积错误放置，能够快速回滚，并继续解释回滚期间已经准入的工作负载如何处理。

最终目标不是让所有 GPU 时刻满载，而是在性能、成本、隔离和交付确定性之间形成可解释的控制回路。一个利用率略低、但排队可预测、故障域清晰、作业可恢复的平台，通常比“卡都很忙、没人知道在忙什么”的集群更有生产价值。
