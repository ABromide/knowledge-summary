推理容量与单位经济学 ​

“这个模型需要多少张 GPU”是容量规划题。同一模型用于离线抽取、流式对话和长上下文 Agent 时，单卡承载能力相差很大。用峰值 tokens/s 除以 QPS 会遗漏长度、尾延迟、突发和显存；用平均 GPU 利用率扩容则会忽略排队。

容量模型要回答：流量带来多少工作；部署在延迟约束内能完成多少；需保留多少余量；每个有效结果消耗多少成本与能量。本文给出从日志、压测到集群的计算框架。

先定义“工作”，再谈 QPS ​

大模型请求至少有三个维度：输入 token I、输出 token O、可复用前缀 C。有效 prefill 约为 I - C，decode 工作约为 O，两者的资源特征不同。只报告 QPS，无法区分短聊天与长报告生成。

容量盘点应从脱敏请求日志构造联合分布，而不是分别取输入、输出平均值。至少按应用、模型、优先级记录：

  • 到达时间与每分钟请求数，包含峰值持续时间和突发系数；
  • 输入 token、输出 token、缓存命中后的实际 prefill token；
  • 流式或非流式、取消位置、超时和重试；
  • 模型、精度、LoRA/适配器、采样与结构化输出配置；
  • TTFT、TPOT/ITL、端到端时延及成功状态。

分别取输入、输出平均值会破坏二者相关性；长输入、长输出请求会占据 KV 更久。应保留样本回放，或建立输入 × 输出二维桶，并单独建模超长上下文。

可先用三个流量指标观察需求：请求/秒表示调度压力，输入 token/秒近似 prefill 压力，输出 token/秒近似 decode 压力。它们不能互相替代。容量表也应明确 tokenizer 版本，因为同一文本在不同 tokenizer 下长度不同。

两道硬约束：显存与服务速率 ​

先算能不能放下 ​

单副本显存预算可写成：

显存需求 = 权重 + KV Cache + 峰值激活/工作区 + CUDA Graph/通信缓冲 + 运行时余量

权重下界约为参数量乘以每参数字节，但量化 scale、元数据和未量化层会让实际值偏高。张量并行会切分大部分权重，却未必等比例切分所有缓冲。KV Cache 则随同时驻留的有效 token增长；它等于所有活跃请求已经 prefill 和 decode 的 token 总和，而不是 API 声明的最大上下文乘以并发。

分页 KV 减少预留与碎片，前缀缓存减少重复计算，但缓存块仍占显存。保留过多旧前缀会挤压活跃请求；低精度 KV、GQA/MQA 和 offload 则引入质量、带宽或尾延迟成本。预算须用引擎可分配 KV 块与实测峰值校准。

再算每秒能服务多少 ​

低负载时，增加并发能把权重读取摊给更多 decode token，吞吐快速上升；到达某一点后，计算、显存带宽、KV 容量或调度器饱和，吞吐曲线变平。继续加压只会让队列和 P99 上升。NVIDIA 的Triton 优化示例也展示了类似现象：并发提升初期增加吞吐，饱和后吞吐几乎不变而时延继续恶化。

所以“最大离线吞吐”不是在线容量。在线单副本容量应定义为：在给定输入/输出分布、到达过程和 SLO 下，能长期稳定承载的最大 offered load。对每个压测点，只有同时满足错误率、TTFT、TPOT、端到端时延和显存安全线，才计入可用区间。

排队：高利用率为何会突然变慢 ​

设平均到达率为 λ，单副本平均服务能力为 μ，利用率可粗略写成 ρ = λ / μ。在最简单的 M/M/1 模型中，平均系统时间为 1 / (μ - λ)。它不是大模型服务的精确预测器——请求长度并非指数分布，batch 让服务时间互相耦合——但揭示了关键事实：当 ρ 接近 1，等待时间不是线性增加，而会急剧发散。

Little 定律 L = λW 同样有用：稳定系统中，系统内平均请求数等于到达率乘以平均停留时间。若到达率不变而 in-flight 请求持续上升，说明停留时间正在增加，系统可能已经过载。对生成服务，最好进一步拆成入口队列、prefill 队列、decode 活跃序列和跨池 KV 传输队列，避免总队列隐藏局部瓶颈。

GPU 利用率不是 ρ。监控中的 GPU busy 可以很高，但 kernel 可能被内存带宽限制，用户请求仍在排队；它也可能不高，却因 KV Cache 已满无法接纳新序列。相反，严格低延迟服务为了吸收突发，本就需要让部分资源在常态空闲。容量控制应优先使用队列时间、in-flight token、KV 占用、抢占/重算和 SLO 达成率，再把 SM、HBM 带宽与功耗作为瓶颈解释指标。

给突发留下什么余量 ​

安全余量不是固定的“GPU 保持 70%”。它取决于扩容启动时间、流量可预测性、故障域和请求最长生命周期。如果新副本下载权重、建立通信组和预热 CUDA Graph 需要数分钟，那么几秒内的流量尖峰不能靠事后自动扩容解决，需要预热副本、入口限流或可降级队列。

可把需求分成基线、可预测峰值和突发：分别由常驻容量、提前扩容、头部空间与准入控制承接。还要做 N+1 演练，验证移除一个故障域后仍满足关键 SLO。

SLO 与 Goodput：只计算用户可用的吞吐 ​

吞吐可以把违约请求也算进去。例如系统每秒完成 100 个请求，其中 40 个 TTFT 超时；从 GPU 视角工作完成了，从产品视角却只有 60 个有效结果。Goodput 把容量定义为满足约定 SLO 的完成率：

Goodput = 单位时间内同时满足正确性、TTFT、TPOT与可用性条件的请求数

DistServe 论文用 goodput 比较聚合与 P/D 解耦配置，核心意义是将系统优化目标从“GPU 做了多少工作”切换为“多少请求按时交付”。但 SLO 需要谨慎制定：TTFT 上限、TPOT 上限、使用 P95 还是逐请求判断，会明显改变结果。不同产品也不应共用一个阈值；交互聊天、后台摘要和离线评测可以进入不同服务等级与队列。

建议形成分层指标：

  1. 用户层：可用性、P95/P99 TTFT、TPOT、端到端时延、取消率。
  2. 流量层：offered QPS、accepted QPS、goodput、输入/输出 tokens/s。
  3. 调度层：队列时间与深度、活跃序列、batch token、抢占和 KV 命中。
  4. 资源层：KV/权重/工作区显存、SM、HBM、互联、CPU、网络和功耗。

NVIDIA GenAI-Perf 文档直接输出 TTFT、ITL、请求与输出 token 吞吐，并可绘制 TTFT 对输入长度等关系；但工具给出的数字仍取决于输入数据与发压方式，不能替代工作负载定义。

从压测结果推导副本数 ​

假设用真实分布压测得到：一个“部署单元”（可能是一张 GPU，也可能是 TP=4 的四卡副本）在 SLO 内可稳定承载 C 请求/秒。预测峰值到达率为 D，容量余量系数为 h，计划允许同时损失 f 个部署单元，则初始估算为：

副本数 N = ceil(D × (1 + h) / C) + f

但这个公式只有在以下条件成立时才有意义：压测与生产模型/精度/引擎/拓扑一致；长度联合分布与缓存命中率一致；C 是稳定 goodput 而非短时最大吞吐；副本间路由近似均衡。若路由按会话粘滞、前缀亲和或 LoRA 分组，热点副本可能先饱和，需要按每个路由分片分别计算。

容量验证应做 offered-load sweep。请求到达最好模拟线上过程；MLPerf 的 Server 场景使用泊松到达并以尾延迟约束下的最大吞吐作为性能指标，可作为方法参考，MLPerf Inference 文档同时保留模型、精度和场景规则，避免把 Offline 与 Server 结果混用。自己的压测还应覆盖：

  • 冷启动与已预热，前缀缓存冷/热两种状态；
  • 常态、预测峰值、突发和持续过载；
  • 短请求被长 prefill 包围的队头阻塞；
  • 单实例故障、扩容、缩容和滚动发布；
  • 客户端取消后服务端是否及时释放 KV；
  • 下游慢读、网络抖动和重试放大。

每个负载点都要运行到预热结束、队列稳定；依赖不断增长的缓存或队列不算稳态。报告须保存镜像摘要、模型 hash、参数、样本和完整分位数，确保软件升级后可复现。

一个从业务峰值到采购数量的算例 ​

假设某问答服务的预测峰值为每秒 18 个请求，脱敏回放显示输入中位数 900 token、P95 为 6000 token，输出中位数 180 token、P95 为 900 token，输入与输出存在明显正相关。团队在四卡部署单元上做泊松到达压测：每秒 5.5 个请求时 P99 TTFT、P99 TPOT 和错误率均满足 SLO；提高到 6.2 后原始吞吐仍增长，但 P99 TTFT 违约，稳定 goodput 反而降到每秒 5.7。因此容量公式中的 C 应取 5.5，而不是 6.2 或离线测试的更高数字。

若为预测误差和突发保留百分之二十五余量，并要求失去一个部署单元后仍承载峰值，计算为 ceil(18 × 1.25 / 5.5) + 1 = 6 个部署单元，即二十四张卡。这个结果仍不是采购结论：先检查故障项是否重复计算。若百分之二十五余量已经明确包含一个副本故障，再额外加一会过度配置；若六个单元跨两个机架，而要求整机架故障，则 f 应按机架内单元数计算。

接着做显存复核。假设回放在目标点测得每单元 P99 活跃 KV 为可分配容量的百分之七十八，长请求突发时到百分之九十二并出现重算，即使延迟压测通过也缺少显存余量。可选择减少每副本并发、把超长请求送到独立池、降低 KV 精度或增加副本，然后重新测量 C。不能简单把六个单元乘以平均 KV，因为路由不均会让热点副本先耗尽。

最后把数量换成财务指标。若一个四卡单元的完全成本为每小时 P，六个单元在目标峰值下每小时交付 T 个满足 SLO 的输出 token，则单位成本为 6P ÷ (T / 1000)。还应分别计算常态低谷：固定六单元常驻时，低谷单位成本可能远高于峰值。若通过定时缩到三个单元能够维持低谷 SLO，节省额才是真正可兑现的弹性收益；仅在压测报告里提高峰值吞吐不会自动降低账单。

排队与 SLO 的现场诊断 ​

线上告警不能只写“P99 升高”。应沿请求路径拆解等待：入口接受前、调度队列、prefill、KV 传输、decode 和流式网络。以下组合能快速缩小范围：

  • 入口队列上涨、GPU 与 KV 都有余量：检查路由限额、会话粘滞、适配器分片和连接池，负载可能没有均匀到达可用副本。
  • TTFT 上涨、TPOT 稳定：检查输入长度漂移、长 prefill 阻塞、前缀缓存命中下降或 prefill 池不足。
  • TTFT 稳定、TPOT 上涨：检查活跃序列、输出长度、显存带宽、decode 池和慢客户端是否占据槽位。
  • 两者同时上涨、吞吐到平台期：系统接近或越过饱和点，应触发准入、降级或提前扩容，而不是继续加并发。
  • KV 高位并伴随抢占重算：先定位超长请求、缓存滞留和取消清理；重算会再次增加 prefill，形成正反馈过载。
  • GPU busy 下降但队列上涨：检查 CPU 调度、tokenizer、网络、跨卡通信、kernel 编译或下游背压，不能据此判断 GPU 过多。

诊断必须关联同一时间窗口的长度分布和版本变更。一次模板升级可能同时增加输入 token、破坏前缀命中并扩大 KV；如果仪表盘只展示 QPS，表现会像“相同流量下系统退化”。限流生效后 GPU 指标恢复，也不等于容量恢复，还要观察拒绝率和 accepted goodput，避免把用户请求丢在系统外后宣称 SLO 正常。

容量上线与成本验收清单 ​

容量方案进入生产前，应逐项签字确认：

  1. 流量样本覆盖工作日、峰值、活动和长尾请求，输入输出保持联合分布；tokenizer 与线上一致。
  2. 容量 C 来自目标 SLO 下的稳定 goodput，测试时长足以观察队列不再增长，并报告置信区间或多轮方差。
  3. 模型权重、量化、引擎、驱动、GPU、互联和全部调度参数有可复现版本，不以厂商理论峰值代替实测。
  4. 目标点同时通过延迟、错误、KV 安全线、取消清理和输出质量门槛；没有用降低质量换取未披露的吞吐。
  5. 单副本、单节点或目标故障域移除后仍满足关键等级；扩容时间、冷启动和缓存预热已经计入。
  6. 入口具备按等级的准入与降级策略，持续过载时不会无限积压并放大重试。
  7. 成本包含主机、网络、存储、空闲副本和平台分摊，分母只使用满足 SLO 的有效请求或 token。
  8. 能效来自整机墙上功率与同一 goodput 窗口，不能拿 TDP 或离线满载结果代替线上能耗。
  9. 已定义重新压测触发器：模型、引擎、硬件、模板、长度分布、缓存命中、SLO 或路由任一显著变化。

只有清单与原始证据一起保存，容量结论才可复核。否则公式里的每个数字都会在几周后失去来源，预算仍会退回到拍脑袋加卡。

成本：从 GPU 小时落到有效 token ​

云账单或折旧只是成本的一部分。部署单元每小时完全成本可写成：

Cost_hour = GPU/主机 + CPU内存 + 本地盘 + 网络 + KV远端存储 + 平台与运维分摊

在测得稳定 goodput 后，可计算：

每千有效输出 token 成本 = Cost_hour / (每小时满足SLO的输出token / 1000)

“有效”很重要：超时后被用户取消、失败重试、为缓存未命中重复 prefill 的计算都应进入分母之外的浪费成本。若业务按请求计价，也应同时报告每千有效请求成本，并按应用拆分输入与输出。长 prompt 的服务可能主要花钱在 prefill，不能用输出 token 单价独自解释毛利。

利用率提高通常降低单位成本，但只到 SLO 膝点为止；越过膝点，违约增多会让 goodput 分母变小，单位有效成本反而上升。量化、小模型路由、前缀缓存和更大 batch 都可能降本，却分别引入质量、路由、命中率与延迟条件。成本评审应同时列出质量门槛和 SLO，而不是只给一列“tokens/$”。

对于自购设备，还要计采购、机房、电力、网络、备件、闲置和折旧周期；对于云设备，要计承诺折扣、可抢占中断、跨区流量和最低租用粒度。不同方案只有在相同的模型质量、上下文能力、可用性与工作负载下才可比较。

能效：测墙上功率，而不是引用 TDP ​

TDP 是散热与功率配置规格，不是这次推理的实际能耗。能量等于功率随时间的积分；单位工作能效可表达为 焦耳/有效输出 token，或其倒数 有效 token/焦耳。应包含整机 GPU、CPU、内存、网卡和电源损耗，并分别报告空闲与负载功耗。

MLPerf Power 方法使用经认可的功率分析仪与协调测量流程；其结果说明强调 Server/Offline 功率在墙上测量，且只对伴随的基准工作负载有效。这个边界很关键：某系统在离线满载时 token/焦耳更高，不代表它在低 QPS、严格 TTFT 的常驻服务中更省电。低流量下，副本空闲基线、最小扩容粒度和跨卡并行都可能主导能耗。

能效优化也存在“更快完成”和“更低瞬时功率”两条路径。提高 batch 可能增加功率，却因更快完成更多有效 token 而降低每 token 能量；功率封顶可能降低瞬时功耗，却延长执行和占用时间。必须测总能量与 goodput，不能凭 GPU 利用率或瓦数单独判断。

一套可持续更新的容量流程 ​

  1. 每周刷新工作负载画像：输入/输出联合分布、缓存命中、到达峰值、取消与重试。
  2. 为每种部署单元维护容量曲线：不是一个 tokens/s，而是 offered load 对 TTFT、TPOT、goodput、KV 与功耗的曲线。
  3. 在 SLO 膝点左侧选工作点：叠加扩容时延、单故障域和流量预测误差形成余量。
  4. 用影子流量或回放验证变更：模型、量化、引擎、驱动和调度参数任一改变，都可能使旧容量失效。
  5. 持续对账预测与实际：比较预测需求、配置容量、实际 goodput 和成本；偏差归因到长度漂移、路由不均、缓存、故障或软件版本。

最终交付物不该是一句“需要 16 张卡”，而应是一份可审计的假设集合：在哪种流量与 SLO 下，哪个版本的四卡部署单元稳定 goodput 是多少，保留何种故障与突发余量，单位有效 token 的成本和能量是多少，以及哪项变化会触发重新压测。这样的容量数字才能进入预算、扩容和架构决策。
