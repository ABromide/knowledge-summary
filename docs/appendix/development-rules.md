# 开发守则

这份守则用于约束知识总结站的内容、前端和发布流程。目标是让每次修改都保持范围清楚、视觉一致、可以验证并且容易回退。

## 1. 开始开发前

### 明确四项输入

开始写代码前，先写清楚：

1. **目标**：用户最终能完成什么事情？
2. **范围**：允许修改哪些页面、组件和配置？
3. **约束**：哪些接口、路由、变量或视觉行为不能改变？
4. **验收**：用什么命令和页面操作证明任务完成？

如果目标存在多种解释，并且不同解释会产生明显不同的结果，应先确认而不是静默选择。

### 先检查来源权利

复刻或整理外部内容时，必须检查许可证、署名要求和素材来源。没有明确许可证时：

- 不复制整篇正文、截图和品牌素材。
- 可以复刻不受保护的功能结构和通用布局。
- 使用独立文字、图形和组件表达总结。
- 在页面末尾列出参考链接和实现说明。

## 2. 保持最小修改

- 每一行改动都应能追溯到当前任务。
- 不重命名无关变量，不调整无关格式，不顺手清理旧代码。
- 不为单一场景提前设计通用框架。
- 重复结构出现两次以上，并且确实需要统一维护时，再提取组件。
- 删除由本次改动产生的无用导入、样式和文件，但不处理历史遗留代码。

## 3. 页面与路由

- 正式内容全部放在 `docs/`，目录名和文件名使用小写英文与连字符。
- 需要保留尾部斜杠的深层路由时，使用 `目录/index.md`。
- 新增或移动页面时同步更新 `docs/.vitepress/config.mts` 中的导航和侧栏。
- 每个页面必须设置准确的标题与描述；特殊页面通过 `pageClass` 隔离样式。
- 内部链接使用站内路径，不硬编码 GitHub Pages 的 `/knowledge-summary/` base。

## 4. 视觉与组件

### 站点视觉基线

| 项目 | 基线 |
| --- | --- |
| 顶栏 | 固定 64px，高层级但不遮挡正文 |
| 桌面侧栏 | 约 272px，紧凑章节列表 |
| 正文 | 最大约 760px，14px / 1.75 行距 |
| 页内目录 | 1280px 以上常驻，窄屏折叠 |
| 品牌色 | 使用 `--knowledge-primary` 语义令牌，深色模式自动切换为更亮蓝色 |
| 圆角 | 卡片 8—12px，控件 6—8px |
| 响应式 | 重点检查 639px、959px、1279px 附近 |

### 组件原则

- 首选 VitePress 原生标题、表格、提示块、代码块和导航能力。
- 章节导读使用 `SummaryHero`，指标使用 `StatGrid`；能用 Markdown 表格和列表表达时不新增组件。
- 需要展示知识链路时使用 `InteractiveFlow`，需要做容量估算、方案权衡或拓扑比较时分别使用 `CapacityLab`、`TradeoffExplorer`、`TopologyExplorer`；前端页面不直接展示 Mermaid 源码块。
- 估算 Widget 必须同时展示计算假设与适用边界，不能把理论上界伪装成生产测量值。
- 交互选项采用 Tabs 或 Toggle Group 的语义结构，支持键盘聚焦，并通过文字而不只通过颜色表达当前状态。
- 论文资料按模型、方法与工程主题直接组织；允许重排标题和段落，但原始正文、公式、链接与图片只能增加，不能删减。
- 论文图片使用 `ZoomableImage`，必须保留替代文本，并验证放大、缩小、关闭和移动端视口。
- 颜色、边框、圆角、阴影和焦点状态使用 `--knowledge-*` 语义令牌，不在组件中维护独立色板。
- 卡片采用中性表面、细边框和克制阴影，状态通过既有变体与语义色表达。
- 组件只负责一种视觉或行为职责，输入通过明确 props 传递。
- 不在 Markdown 中堆叠大段重复内联样式。
- 页面专属选择器必须带页面类，例如 `.knowledge-home`。

### 可访问性

- 使用语义化标题层级，不跳过必要层级。
- 图片必须提供能说明内容的替代文本。
- 按钮必须有可理解的文字或 `aria-label`。
- 不只依靠颜色表达状态；同时提供文字、图标或形状。
- 浅色、深色模式都要保持足够对比度和可见焦点。

## 5. 内容质量

- 一篇总结至少包含问题、结论、证据、限制和下一步。
- 区分已验证事实、来源观点和作者推断。
- 时效性内容标注日期，并优先链接到一手来源。
- 代码示例必须足够小，且与正文结论直接相关。
- 不使用大段空泛口号替代可执行步骤。

### Notion 总结规则

- 先读取父子关系、数据库属性和页面正文，再确定站内分组。
- 每篇总结末尾保留 Notion 来源链接，并同步更新来源索引。
- 合并重复内容，但不删除或修改原始 Notion 页面。
- 只有标题或收藏链接的页面标记为待消化，不补写不存在的结论。
- 时效性日报和趋势报告标明快照日期，不作为长期事实直接引用。

## 6. 安全与依赖

- 不把密钥、Cookie、访问令牌、个人信息和生产数据写入仓库。
- 外部链接使用 HTTPS；新窗口链接添加 `rel="noreferrer"`。
- 新增依赖前说明必要性，优先使用现有依赖或浏览器能力。
- 用户输入进入 HTML、URL 或命令前必须经过正确的转义或校验。
- 高风险功能需要单独的威胁分析、权限边界和失败回退设计。

## 7. 运行与验证

所有操作通过脚本完成：

```bash
./scripts/setup.sh   # 安装依赖
./scripts/dev.sh     # 本地开发
./scripts/check.sh   # 构建与静态产物检查
./scripts/audit.sh   # 依赖安全审计
./scripts/preview.sh # 预览构建产物
./scripts/deploy.sh  # 发布 GitHub Pages
```

合入前至少完成：

- 构建成功，目标深层路由产物存在。
- 桌面与移动端无横向溢出。
- 浅色与深色模式内容可读。
- 侧栏、页内目录、复制按钮和站内链接可用。
- 依赖审计没有未解释的高风险问题。

## 8. Git 与发布

- 提交只包含当前任务文件，提交信息使用简洁中文。
- 推送前检查工作区和实际 diff，不提交缓存与构建目录。
- 发布使用 `./scripts/deploy.sh`，由脚本构建并更新 `gh-pages` 分支。
- 发布完成后检查 GitHub Pages 状态、线上 HTML、CSS/JS 和每个一级分组至少一个深层路由。
- 只有本地产物、远程资源和浏览器可见结果一致时，才能报告上线完成。

## 完成定义

任务只有同时满足以下条件才算完成：需求范围内的功能已经实现，构建与审计通过，页面在目标尺寸可用，文档和导航同步更新，线上结果经过实际访问验证，并且不存在未说明的失败或权限问题。
