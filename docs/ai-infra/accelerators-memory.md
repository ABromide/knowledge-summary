# 加速器、HBM、精度与 Roofline

AI 加速器的规格表把计算、显存、互连和功耗压缩成一排峰值数字，但真实工作负载不会同时命中全部峰值。矩阵单元可能等待 HBM，HBM 可能等待地址生成和同步，足够大的模型可能被容量迫使跨卡，低精度峰值又可能受缩放和精度校验限制。理解硬件的关键不是背诵“多少 TFLOPS”，而是为每个热点路径回答三个问题：做多少运算、移动多少字节、数据在哪一级存储之间移动。

## 1. 加速器不是一块更快的通用处理器

通用 CPU 擅长低延迟控制流、复杂分支和大容量主存；AI 加速器则用大量并行执行单元、矩阵乘加阵列和高带宽片上/封装内存，提高规则张量计算的吞吐。一次 kernel 启动后，线程块被调度到多个计算单元，每个计算单元还要在寄存器、共享存储或片上缓存之间复用数据。能否形成足够并行度、能否连续取数以及形状是否适合矩阵指令，往往比源代码中的算术表达式更决定速度。

以 NVIDIA Hopper 为例，Tensor Core 面向密集矩阵乘加，Tensor Memory Accelerator 可以在全局内存和共享内存之间搬运一至五维张量。官方调优指南说明，TMA 允许单线程发起大块异步搬运，减少搬运占用的寄存器和 SM 指令，让计算在线程块真正消费数据前与传输重叠。[NVIDIA Hopper Tuning Guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html)

这揭示了加速器优化的基本结构：把大问题切成适合片上空间的 tile，提前加载下一块，在矩阵单元上计算当前块，再把结果合并写回。分块过小会增加启动和同步开销，过大又会消耗过多寄存器或共享内存、降低可同时驻留的线程块数量。所谓 occupancy 也不是越高越好；只要已有足够并发隐藏延迟，继续压低单线程资源来追求占用率，可能反而增加指令和数据搬运。

## 2. 峰值算力必须带着限定条件阅读

一张卡通常同时列出 FP64、FP32、TF32、BF16、FP16、FP8 和整数性能，有的数字还附带结构化稀疏条件。这些值属于不同指令路径，不能横向拼接。例如科学计算需要 FP64 数值范围，Transformer 训练常使用 BF16/FP16 矩阵路径，推理可能采用 FP8 或 INT8；如果 kernel 形状、数据布局或库版本不能进入对应矩阵指令，标称峰值就没有意义。

还要区分向量峰值和矩阵峰值、稠密值和稀疏值、单芯片和整机值、SXM/OAM 与 PCIe 形态。NVIDIA 官方 H100 页面列出的 HBM 带宽会随具体形态变化；AMD 官方 MI300X 规格给出 192 GB HBM3 和约 5.3 TB/s 理论峰值带宽。两组数字说明硬件设计在算力与内存间的不同取舍，但不能据此直接宣布某型号更快，必须代入目标精度、内核、软件栈、功耗和多卡拓扑。[NVIDIA：H100 Tensor Core GPU](https://www.nvidia.com/en-eu/data-center/h100/) [AMD：Instinct MI300 系列](https://www.amd.com/en/products/accelerators/instinct/mi300.html)

## 3. HBM 同时解决带宽、容量和能效问题

HBM 通过多层 DRAM 堆叠、硅通孔和宽接口，在加速器附近提供远高于普通主存接口的并行数据通道。它的价值不只是单根引脚更快，而是以宽总线和更短数据路径提高总带宽及每比特能效。Micron 的 HBM3E 产品资料描述了 8‑high、24 GB 堆叠和超过 1.2 TB/s 的单堆叠带宽，并强调先进封装、TSV 与 RAS 能力；实际整卡容量和带宽取决于堆叠数量、控制器与系统实现。[Micron：HBM3E Product Brief](https://assets.micron.com/adobe/assets/urn%3Aaaid%3Aaem%3Ab710d8f2-7f66-44c1-a234-456e2b986347/original/as/hbm3e-product-brief.pdf)

容量与带宽是两个不同约束。模型权重、训练状态、激活和推理 KV Cache 首先必须放得下；放得下之后，算子每秒还必须获得足够字节。容量不足会触发张量并行、CPU/NVMe offload 或更激进量化，随之引入互连通信和调度复杂度。带宽不足则表现为计算单元大部分时间等待数据，即使显存仍有空余，增加 batch 或融合算子才可能提高复用。

HBM 也不是唯一内存层次。典型路径包括主机内存、设备 HBM、L2、共享内存和寄存器，越靠近计算单元通常容量越小、带宽越高、管理越细。性能优化本质上是在有限片上空间里增加复用：同一块权重或激活从 HBM 读取一次后，尽可能完成更多乘加。FlashAttention 一类 I/O 感知算法的收益，正来自重排分块与在线归一化，避免将完整注意力中间矩阵反复写回 HBM，而不是减少了注意力定义本身。

采购时还应把 ECC、故障隔离、页退休和可观测性纳入容量。标称容量不是应用可用容量，运行时、通信 buffer 和可靠性机制都有占用；长期训练更关心可持续带宽、热稳定与错误恢复，而非短时峰值。

## 4. 低精度是系统设计，不是类型替换

浮点格式用符号位、指数位和尾数位在动态范围与精度之间取舍。FP16 有较多尾数位但指数范围较小，BF16 保留与 FP32 相同宽度的指数而减少尾数，通常更易承受训练中的数值范围；TF32 是特定矩阵计算路径，不等同于把所有张量存成新格式。FP8 进一步减少存储和带宽，并提高矩阵吞吐，但更依赖缩放策略与高精度累加。

FP8 格式论文提出 E4M3 与 E5M2 两种编码：前者给更多尾数精度，后者用更多指数位扩大动态范围。论文在 CNN、RNN 和 Transformer 上实验，并覆盖到 175B 参数语言模型，展示了在适当混合精度策略下接近 16 位训练质量的可行性。这是一项实验结论，不意味着任意模型、任意张量都能无校准切换为 FP8。[《FP8 Formats for Deep Learning》](https://arxiv.org/abs/2209.05433)

训练系统通常让矩阵输入使用较低精度，乘加在硬件支持的路径执行，在更高精度中累加，并为主权重、优化器状态或敏感算子保留较高精度。还可能使用 loss scaling、动态范围统计、逐张量或逐块缩放。推理量化则要区分权重、激活和 KV Cache：仅量化权重主要减少权重容量和读取字节，激活量化才能进一步触及中间数据，但校准难度和误差风险更高。

这个精度实验应允许比较每元素字节数、理论矩阵吞吐、动态范围和预期误差，并明确标注“硬件支持”与“质量已验证”是两件事。任何选择都必须经过基准模型的 loss、下游任务和异常值测试。

CUDA 官方最佳实践提醒，浮点运算不满足结合律，FMA 与分开的乘加也可能得到不同结果；并行化改变归约顺序后，不应默认与串行结果逐位一致。验证应使用与业务相符的误差界和参考输出，同时保留 NaN/Inf、梯度范数和长期收敛监控。[CUDA C++ Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)

因此精度评审至少同时检查：最终质量是否达标、训练是否长期稳定、实际 kernel 是否命中低精度路径、显存与带宽是否真的下降，以及格式转换是否产生新的开销。只看到显存少了一半，不能推导端到端速度会翻倍。

## 5. Roofline 把运算和数据移动放在同一张图上

Roofline 模型由 Williams、Waterman 与 Patterson 提出，用算术强度连接处理器峰值算力与内存带宽。算术强度 `I` 定义为完成的浮点操作数除以从目标内存层次搬运的字节数，单位是 `FLOP/Byte`；可达到的性能上限近似为：

`P_attainable = min(P_peak, B_memory · I)`

横轴是算术强度，纵轴是 FLOP/s。低强度区域受斜向带宽屋顶限制，属于 memory-bound；高强度区域触及水平计算屋顶，属于 compute-bound。二者交点 `I_ridge = P_peak / B_memory` 是脊点：工作负载强度低于它时，单纯增加计算单元不会改善上限；高于它时，继续节省 HBM 字节的收益开始减小。[《Roofline: An Insightful Visual Performance Model》](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-134.pdf)

上面的交互 Roofline 应允许切换精度峰值和内存带宽、拖动工作负载强度，并显示脊点。把 FP16 改成 FP8 后，计算屋顶可能上升、字节数也可能下降，脊点随之移动；这比孤立比较峰值更接近真实决策。

Roofline 是上界模型，不是性能承诺。它默认已知实际数据流量和有效运算数，还没有自动表达 kernel 启动、依赖、分支、同步、通信、缓存冲突和形状利用率。实际分析应为 HBM、L2 或片上共享存储建立不同屋顶，并把 profiler 测到的字节而非仅靠源码推导的最小字节代入。若实测点远低于对应屋顶，说明还有其他限制，需要继续查看指令吞吐、并发度或调度时间。

## 6. 把 Transformer 热点放回 Roofline

大矩阵乘法在 `M、N、K` 足够大且分块良好时，输入块可被大量乘加复用，算术强度较高，容易接近 compute-bound。小 batch、细长矩阵或 decode 阶段的矩阵向量形状则复用较差，更容易受权重读取带宽限制。相同模型在 prefill 和逐 token decode 上可能落在 Roofline 的两侧，所以“这个模型是算力密集型”并不是完整描述。

逐元素激活、归一化和简单归约通常每读取一个元素只做少量计算，算术强度较低。优化重点是合并相邻操作、减少中间张量落到 HBM，并进行向量化访问，而不是手工增加算术指令。注意力的瓶颈随序列长度、batch、头维度和实现变化；应测量 QKV 投影、score、softmax、加权求和及 KV Cache 读取各阶段，避免给整层贴一个标签。

算子融合能减少启动次数与 HBM 往返，却会增大 kernel、寄存器压力和编译复杂度。只有当被融合边界确实产生显著内存流量或启动开销时才值得做。对于已经由成熟库高效实现的大 GEMM，随意融合前后处理还可能破坏库的最佳分块。

## 7. 用三维预算完成硬件选型

对候选工作负载分别建立：

1. **容量预算。** 权重、训练状态、激活、KV Cache、临时空间和安全余量是否放得下；放不下会引入什么并行或 offload。
2. **带宽预算。** 每步或每 token 从 HBM 与互连搬运多少字节，可持续带宽下的最低时间是多少。
3. **计算预算。** 各精度的有效 FLOPs、矩阵形状利用率和非矩阵算子占比，理论最低时间是多少。

将计算下界、HBM 下界和通信下界分别列出，再与端到端实测对比。若 HBM 下界最大，优先量化、融合、缓存和批处理；若计算下界最大，优先更高效矩阵路径、并行分块和减少无效 FLOPs；若通信下界最大，则调整拓扑映射或并行策略。最后再加入功耗、可靠性、软件成熟度和采购可用性。

验证必须使用目标 batch、序列长度分布、模型版本和服务约束，至少报告中位数与尾延迟、稳态吞吐、可用显存、功耗和质量结果。峰值数字负责画屋顶，真实 trace 决定工作点；二者结合，硬件选型才从品牌比较转为可复现的系统判断。

### 一次最小但可信的测量

先用框架 profiler 标记预热期与稳态区间，只统计稳态的多次迭代；同时采集 kernel 时间、HBM 读写字节、矩阵指令利用率和功耗。随后分别改变 batch、序列长度与精度，每次只改变一个变量，并确认输出质量仍在约定误差内。对于分布式任务，再增加单卡、单节点和多节点三个层级，分开计算本地算子效率与扩展效率。

测量结果应保留原始 trace 与环境指纹：设备固件、驱动、运行库、编译器、时钟或功耗上限、容器镜像和模型提交。若一次“优化”只在首次编译缓存、异常高时钟或更宽误差阈值下成立，它就不是可部署收益。短 microbenchmark 用来解释屋顶，端到端回放用来确认用户工作负载；缺少任一层，结论都容易把局部峰值误当成系统改善。

## 8. 误区诊断：低精度峰值更高，服务却没有加速

设想把一个生成服务从 BF16 切换到 FP8，规格表中的矩阵峰值显著提高，权重占用也下降，但实际逐 token 延迟几乎不变。最常见的错误结论是“量化实现失效”。更可靠的诊断应从工作点开始：decode 的小批次矩阵可能本来就在 Roofline 脊点左侧，每生成一个 token 都要重新读取大部分权重，矩阵单元并非主要上限。FP8 虽减少字节，却可能新增反量化、缩放统计和格式转换；若这些操作没有融合，节省的 HBM 时间会被额外 kernel 启动抵消。

先确认端到端请求形状。离线基准常用固定大 batch，把 GEMM 推到计算密集区；线上却受并发和尾延迟限制，batch 较小且持续变化。应按真实输入长度、输出长度和并发分桶，分别绘制 prefill 与 decode 的 Roofline 工作点。若 prefill 明显加速而 decode 不变，不能用整体平均掩盖阶段差异，而应判断产品流量究竟由哪一阶段主导。

再检查低精度路径是否完整。权重虽然保存为 FP8，运行时可能因不支持的维度、对齐或算子回退到 BF16；部分归一化、softmax 和输出层也可能仍由高精度执行。用 profiler 核对实际指令、每层输入输出格式和转换 kernel，区分“存储压缩”与“低精度计算”。同时检查缩放粒度：逐张量缩放元数据少但更易受异常值影响，逐通道或逐块缩放质量更稳，却增加元数据访问与实现复杂度。

最后检查释放的容量是否转化为系统收益。显存下降只有在允许更大 batch、更多 KV Cache 或减少张量并行时才会提高服务吞吐。如果调度器仍沿用原并发上限，或者容量余量被静态预留，量化的价值不会自动出现。相反，扩大 batch 后还要重新测量首 token、逐 token 和高分位延迟，不能只报告总 tokens/s。

### 加速器方案的验收清单

- 规格表中的峰值已注明精度、稀疏、形态、功耗上限和单卡或整机口径，没有混合不可比较数字。
- 容量预算使用应用可用显存，并包含运行时、通信、临时工作区、KV Cache 或训练状态及安全余量。
- 目标形状的 profiler 证明关键算子进入预期矩阵指令，未把隐式回退或格式转换计为低精度收益。
- Roofline 使用实测 HBM 字节和可持续带宽，分别标注计算受限、内存受限及无法由基础屋顶解释的热点。
- 数值验收覆盖代表数据、长尾异常值和长时间训练或生成，误差阈值在优化前确定，不能为了通过而临时放宽。
- 分布式测试同时报告单卡效率与扩展效率，互连、集合通信和跨节点映射造成的损失可单独复现。
- 端到端结果包含预热策略、中位与高分位延迟、吞吐、显存、功耗和失败率，并保存可回放的原始 trace。

验收的目标不是证明新硬件的某个数字更大，而是确认它在目标约束下改变了真正的瓶颈，并且收益能够跨多次运行、软件重启和生产形状稳定复现。
